# Delta — Product Requirements Document v1

## 1. Problem

A Physics PhD student at IISc Bangalore does experimental research in condensed matter physics — thin film deposition, materials characterization, device fabrication. Her problem is paper discovery and synthesis:

- Her field's papers live in Physical Review, Nature Materials, Advanced Materials, Journal of Applied Physics — not on arXiv. Standard tools miss her domain entirely.
- Finding papers is manual and slow. Connecting them (how does this method relate to that one? what do these three papers disagree on?) is something she does in her head with no tooling support.
- Paid agents (Bohrium, ~$60/month) are too expensive and hard to use. NotebookLM has no search. arXiv search is irrelevant for her.
- She is not technical. She cannot install software, run commands, or configure anything.

Delta is a hosted web app she opens in a browser. It finds papers, reads them, and synthesizes what they say — in plain language, with citations she can verify.

## 2. Users

**Primary:** Physics PhD student, IISc Bangalore. Non-technical. Uses Delta to discover papers, understand a field, prepare for lab meetings and literature reviews. Domain: experimental condensed matter, thin film deposition, materials science.

**Secondary:** The developer (ML scientist, Expedia Group Ads AI). Uses Delta for his own research (ML, interpretability, arXiv-heavy). Also serves as the tester and dogfooder.

Two users. No multi-tenancy, no RBAC, no user management infrastructure needed in v1.

## 3. Core Modes

Two buttons. No slash commands in v1.

### 3.1 Quick Answer

- **Trigger:** User types a question, clicks "Quick Answer"
- **Behaviour:** Delta may ask one clarifying question if the query is too vague. Then searches, retrieves, synthesizes. Returns a conversational response with inline citations.
- **Time budget:** Target < 60 seconds end-to-end
- **Output:** Chat-style response, inline paper citations (numbered), 3–5 papers referenced

### 3.2 Deep Research

- **Trigger:** User types a question, clicks "Deep Research"
- **Behaviour:** Delta generates a research brief, fans out to parallel sub-searches, retrieves and reads full text where available, synthesizes across papers. Streams output as it builds.
- **Time budget:** 2–5 minutes, with visible progress
- **Output:**
    - Structured report: Background -> Current State -> Methods / Findings -> Open Questions -> Recommendations
    - Main paper list: 5 curated papers with per-paper synthesis paragraph
    - Appendix paper list: up to 20 additional relevant papers, title + one-line note
    - All citations link to publisher page and open-access PDF where available

### 3.3 Follow-up (always available)

After either mode, the chat window stays active. She can ask follow-ups ("what does paper 3 say about temperature?", "find newer papers on this", "summarise in simpler terms"). These run as Quick Answer by default unless she explicitly triggers Deep Research.

## 4. Session Model

### 4.1 Structure

Each session is a **linear thread** stored as a sequence of messages, each with a `parent_id`. A session is a path through this tree from root to current leaf.

**Branching:** At any message in the thread, she can click "Branch from here." This creates a new session with `parent_session_id` and `branch_from_message_id` set, and a copy of the conversation up to that point as context seed. The original session is unchanged. The UI shows sessions as a flat list; branching creates a new entry in that list (linked to parent, but navigated independently).

**Branch summary:** When a branch is created, a cheap model generates a one-paragraph summary of the branched-off conversation. Stored as `branch_summary` on the parent session. Shown in the session list as context.

### 4.2 Session Metadata

Each session has:

- `id`: UUID
- `title`: auto-generated by cheap model after first exchange, max 10 words
- `summary`: running bullet list, auto-updated by cheap model at session end (or after each Deep Research run). Max 10 bullets. New bullets appended; oldest dropped when limit exceeded. Not a full transcript — key findings and papers seen.
- `tags`: user-defined, max 5 per session
- `created_at`, `updated_at`
- `parent_session_id`, `branch_from_message_id` (nullable)

### 4.3 Session Resumption

Sessions are stored persistently. She can:

- See a list of past sessions (title, date, first bullet of summary)
- Search sessions by text (matches title + summary bullets)
- Open any past session and continue from its current leaf
- Branch from any past session's any message

Delta has an internal `list_sessions` and `search_sessions` tool so the agent can answer "what did we find last time about MoS2?"

### 4.4 Storage

SQLite via aiosqlite. Tables: `sessions`, `messages`, `papers_seen`. No Postgres, no Redis. Fine for 2 users.

## 5. User Memory

Each user has a persistent memory file. Updated by a cheap model after each session. Not loaded wholesale into every prompt — Delta reads it at session start and injects relevant excerpts.

**Contents:**

- Research context: what she's working on right now, her PhD topic, her lab's focus
- Seen papers: DOIs / paper IDs of papers Delta has already retrieved and summarized for her (avoids re-fetching and re-summarising)
- Preferences: output verbosity, whether she wants methodology detail, etc.
- Recurring topics: "she frequently asks about MoS2 deposition, PVD, sputtering, ALD"

**Update mechanism:** At session end, the cheap model rewrites the memory file (not appends). Old information is naturally compressed or dropped. No hit counter in v1 — that is v2.

**Storage:** Flat markdown file per user, stored in the database as a text field on the `users` table. Simple.

## 6. Paper Access Stack

Delta fetches full text server-side via this waterfall. Each step tried in order:

```
1. Semantic Scholar API      — metadata, abstract, citation graph, open access PDF URL
2. OpenAlex API              — metadata, abstract, open access links
3. Unpaywall API (by DOI)    — best legal free PDF URL (green OA, institutional repos)
4. CORE API                  — aggregated OA full text from repositories globally
5. arXiv API                 — preprint if available (physics groups sometimes post)
6. User upload               — she downloads on IISc WiFi, uploads PDF to Delta
```

**Deduplication:** by DOI across all sources. A paper found in both Semantic Scholar and OpenAlex is one record.

**What happens with abstract-only papers:** They are included in results but flagged ("Full text unavailable — abstract only"). The LLM reasons over the abstract. The paper is included in the paper list with a note. She can upload the PDF to unlock full synthesis.

**Full text processing:** PDFs are extracted to markdown. Long papers are chunked. Only the most relevant chunks (by embedding similarity to the research query) are included in the synthesis prompt. Token budget is enforced — the synthesis model never receives more than fits in its context window.

## 7. Architecture

### 7.1 Tech Stack

- **Backend:** Python 3.11+, FastAPI, uvicorn
- **Agent loop:** LangGraph (StateGraph, Send, SqliteSaver checkpointer)
- **LLM gateway:** LiteLLM
- **Primary model:** DeepSeek v3 (cheap, capable, good for synthesis)
- **Cheap model:** DeepSeek v3 at lower temperature / or a smaller model for summaries, memory updates, title generation
- **Streaming:** FastAPI SSE (Server-Sent Events)
- **Database:** SQLite via aiosqlite
- **Hosting:** Render (always-on $7/month tier — no cold starts)

### 7.2 Graph Topology

```
START
  │
  ▼
load_context          [deterministic] load user memory + session history
  │
  ▼
clarify_or_plan       [LLM] decide: ask clarifying question OR generate research brief
  │                         structured output: {action: "clarify"|"search", brief: str, question: str}
  ├─ clarify ──────────────► END (wait for user reply)
  │
  └─ search
        │
        ▼
      route_mode      [deterministic] Quick Answer vs Deep Research (from button click, not LLM)
        │
        ├─ quick ──► single_search ──► synthesize_quick ──► END
        │
        └─ deep
              │
              ▼
            plan_subtopics    [LLM] break research brief into N subtopics (max 5)
              │
              │  Send × N
              ▼
            search_subtopic   [deterministic + LLM] search APIs -> fetch full text -> extract relevant chunks
              │  (parallel, each is independent)
              │
              ▼
            compress_subtopic [LLM, cheap model] summarize findings per subtopic
              │
              ▼  (all parallel results collected)
            synthesize_deep   [LLM] write structured report + paper list
              │
              ▼
            update_memory     [LLM, cheap model] update user memory file
              │
              ▼
            update_session    [LLM, cheap model] update session summary bullets
              │
              ▼
            END
```

### 7.3 Agent State

```python
class DeltaState(TypedDict):
    # Input
    messages: Annotated[list, add_messages]       # full conversation thread
    user_id: str
    session_id: str
    mode: Literal["quick", "deep"]                # set by button, not LLM

    # Research
    research_brief: Optional[str]                 # structured query for search
    subtopics: Annotated[list[str], override_reducer]
    raw_results: Annotated[list[PaperResult], override_reducer]   # per-paper: id, doi, title, abstract, full_text, chunks
    compressed_findings: Annotated[list[str], override_reducer]   # per subtopic
    visited_paper_ids: set[str]                   # dedup across parallel searchers

    # Output
    final_report: Optional[str]
    paper_list: Annotated[list[PaperCard], override_reducer]

    # Context (loaded at start, written at end)
    user_memory: str
    session_summary: list[str]
```

### 7.4 Tools (what the LLM can call)

All tools return structured data. The LLM never constructs citations directly — citations are assembled by code from tool outputs.

```python
# Paper discovery
semantic_scholar_search(query: str, limit: int) -> list[PaperResult]
semantic_scholar_paper(paper_id: str) -> PaperResult
semantic_scholar_citations(paper_id: str) -> list[PaperResult]   # forward citation chaining
openalex_search(query: str, filters: dict) -> list[PaperResult]

# Full text access (waterfall, tried in order)
fetch_full_text(doi: str) -> FullTextResult   # tries Unpaywall -> CORE -> arXiv internally

# Session / memory
list_sessions(user_id: str, query: Optional[str]) -> list[SessionSummary]
get_session_summary(session_id: str) -> str
```

**Tools the LLM cannot call (deterministic only):**

- Deduplication by DOI
- Token budget enforcement
- PDF extraction and chunking
- Relevance scoring and ranking
- Citation formatting
- Memory file read/write (triggered by graph, not LLM tool call)

## 8. Deterministic vs LLM Boundary

**LLM decides:**

- Whether to ask a clarifying question or proceed
- What search queries to generate from the research brief
- Which returned papers are actually relevant (structured output: paper_id + relevance score + reason)
- How to synthesize findings across papers into a narrative
- Memory file content (rewrites it based on session)
- Session title and summary bullets

**Code decides:**

- Which mode (Quick / Deep) — comes from button click
- API calls and their parameters (code calls the API, LLM just provides the query string)
- Deduplication by DOI
- Paper ranking (citation count × recency × LLM relevance score)
- What goes into the final paper list (code assembles from PaperCard objects)
- Token budget allocation
- All citations in the final output (assembled from retrieved PaperResult objects, not generated by LLM)
- Session storage, memory file I/O
- Retry logic on API failures

**The invariant:** Every paper cited in Delta's output exists in `raw_results` for that session. The LLM can only reference papers by their `paper_id`. Code resolves paper_id -> full citation. If the LLM invents a paper_id that doesn't exist in the session's retrieved set, it is silently dropped.

## 9. API Layer

### 9.1 Endpoints

```
POST /sessions                          create new session
GET  /sessions/{id}                     get session + messages
POST /sessions/{id}/messages            send message (returns SSE stream)
POST /sessions/{id}/branch/{message_id} branch from message
GET  /sessions                          list sessions (with search query param)
POST /papers/upload                     upload PDF for a paper
GET  /health
```

### 9.2 SSE Streaming

The `POST /sessions/{id}/messages` endpoint returns an SSE stream. Events:

```
event: thinking        data: {"text": "Searching for papers on..."}
event: paper_found     data: {"paper_id": "...", "title": "...", "year": ...}
event: section_start   data: {"section": "Background"}
event: content_chunk   data: {"text": "..."}
event: done            data: {"session_summary": [...]}
event: error           data: {"message": "..."}
```

Frontend renders each event type differently — thinking is shown as a status bar, paper_found adds a card to the side panel, content_chunk streams into the main response area.

## 10. Frontend

Hosted web app. React (Vite). No local setup, no install. She opens a URL.

**Layout:**

```
┌──────────────────────────────────────────────────────┐
│  Sessions sidebar  │  Main chat area                 │
│                    │                                 │
│  [+ New session]   │  [message thread]               │
│  Session list      │                                 │
│  (title + date)    │  [text input]                   │
│                    │  [Quick Answer] [Deep Research] │
└──────────────────────────────────────────────────────┘
```

**Paper cards** appear in the main area as Delta finds them. They are not a separate panel — they appear inline in the response as Delta streams.

**No settings page in v1.** No model selection, no config. It just works.

## 11. Out of Scope for v1

- MCP integration
- Knowledge graph / connection visualization
- Multi-user support, auth (basic password protection is fine)
- Persistent domain knowledge accumulation (v2)
- Memory hit counter / decay scoring (v2)
- Automatic intent detection for mode selection (v2 — buttons for now)
- NotebookLM-style audio / podcast
- Paper annotation or note-taking within Delta
- Experiment replication or code execution
- Redis / Postgres

## 12. Build Order

1. `tools/semantic_scholar.py` — search, paper details, forward citations
2. `tools/full_text.py` — Unpaywall -> CORE -> arXiv waterfall, PDF extraction
3. `tools/openalex.py` — supplementary search
4. `graphs/research.py` — the LangGraph graph (state, nodes, edges)
5. `graphs/memory.py` — memory read/write nodes
6. `api/app.py` — FastAPI app, SSE endpoint, session routes
7. `api/session_store.py` — SQLite session + message persistence
8. Frontend — React app, session sidebar, chat area, streaming paper cards
9. Deploy to Render

Each step is independently testable. Steps 1–3 can be run from a Python script before any graph exists. Step 4 can be tested with a CLI runner before any API exists. Frontend is last.

- Estimated 100 Quick Answer runs/month: ~$0.50
- Semantic Scholar API: free
- OpenAlex API: free
- Unpaywall API: free
- CORE API: free tier (10K requests/month)
